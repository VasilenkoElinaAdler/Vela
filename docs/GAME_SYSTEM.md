# Vela Elina — single game system
## Status
Decision 014: mandatory architectural rule from the owner, 2026-11-28. All modules inherit one system. Prior owner requirements (Nov 6): new game starts with 10 hearts and 0 stars; errors reduce health; stars accrue for completed tasks; no approved global star maximum; zero hearts presents Restart or Exit. Equal visual width of heart/star rows, actual progress only, Inicio always accessible, success text only after real success. Four-language architecture, offline, one Bubble Gum theme, one replaceable typography family.
## Unified model
- GameRules: only canonical source for initial health, scoring, error cost, transition rules and rewards. Distinguish approved constraints from proposed balance. No module-specific numeric constants for hearts or stars.
- GameProgress: one versioned, locally persisted source of run health, run-earned stars, accepted task completion IDs, current lesson/level, terminal state. Separate permanent collection confirmations and achievements from transient run values. Keep existing card IDs and legacy progress; migration must be tested, never silently delete existing knowledge.
- GameReducer: one atomic accepted-answer operation. UI emits task ID and validated result; rule engine decides whether event is accepted, effects, and next state. No duplicate awards/loss from double taps, retries, recomposition or restarting app. Gameplay modules only validate subject-specific answers, choose task presentation and render local animation (e.g. regatta position).
- ProgressHeader: one shared component. Ten heart positions; stars represent real earned tasks, with no arbitrary global maximum. If a level displays a finite goal, derive it from its actual approved task catalog and distinguish it from cumulative stars. Equal visual row widths; use numeric counts/compact indicators for larger totals. No UI mock counter becomes gameplay balance.
- Audio: common local success/error feedback; each topic can additionally play its own pronunciation/educational sound. No required network.
## Proposed defaults for explicit owner approval before runtime integration
1. A new playthrough starts at 10 hearts, 0 run stars. Carry the remaining hearts and cumulative run stars through lesson transitions and return to Inicio. Resume the same run after closing/reopening. No automatic health refill at each lesson, no time penalty. Restart explicitly begins a new run; exit preserves permanent collection and completed learning records. Confirm whether abandoning unfinished run clears it or offers resume (recommend resume until explicit Restart).
2. An accepted wrong answer costs one heart, does not subtract already earned stars, and gives feedback. Correct completion earns one star exactly once per unique task ID within the current run. Repeated taps or retrying an already rewarded task do not farm stars. Wrong taps can be retried after feedback; empty background taps outside a valid target are ignored. These numeric reward/cost and retry rules are proposals, although both current prototypes already use one heart/one star.
3. Level means an approved learning unit, not an arbitrary score band. Complete all required task IDs for that level to unlock the next; no fixed global star cap or invented thresholds. Number of tasks comes from the approved lesson content. Repetition can support learning without automatically adding more rewardable tasks. No new lesson implemented before Parts passes child testing.
4. Zero hearts stops input/rewards; show Restart and Exit. Permanent card collection is not erased by run failure. Winning and local race result remain distinct from overall life/level state. Regata remains accessible as an existing activity, and uses the same accepted-answer rules; exact opponent pacing/finish threshold remain activity-specific, explicit documented tuning, not separate heart/star rules. Existing two-confirmation album mechanic remains intact, and no new trophy/cosmetic economy is introduced.

4. Compile only after unified system integration and first-lesson art/audio archive is available; test the first topic on actual Android and supervised children. Freeze expansion/translation and optimization distractions until engagement gate passes.
## Change control
Before any new lesson, check existing rules/UI/state/services. Reuse by default; document any genuine need for an exception, impact on gameplay and tests, and wait for owner approval before implementing it. Keep one canonical specification and increment its decision log. Visual samples are not authority for numerical game rules. 

## Current product direction — Decision 015
The owner has described a finite progression: untimed interactive training (hearts and earned stars) → star-based qualification → timed regatta mixing previously learned material (existing cards retained) → cups → Captain's Passport → game complete. This supersedes the earlier concept of regata as the default instructional mode. Training and competition remain parts of one centrally managed system; mode-specific consequences must be explicit, not independent hidden rule sets. Proposed competition exception: time/position penalty instead of heart loss. Qualification threshold of 10 stars and completion target of 10 cups are examples, not final balancing decisions. Avoid farming repeat awards; distinct escalating regattas are a proposed way to achieve this, not approved final scope. See REWARDS.md.
For the next test APK, implement only the common progress rules needed by the first interactive lesson and preserve the existing card/regatta source and data. Do not implement the complete timed competition progression, new topics, passport screen, camera/selfie or new artwork in this milestone. Exact training error cost/recovery, qualification criteria and race timing are to be settled within the shared system; do not silently reuse divergent prototype numbers or present unimplemented mechanics as working. First-lesson APK is an engagement/functional test, not the completed game.
